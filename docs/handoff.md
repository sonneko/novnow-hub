## 4. M3 実装判断（thin slice での方針）

M3 の公開フロー実装において、仕様・設計に明記が無く判断が必要だった点を次に定める。いずれも契約（`api/openapi.yaml`）は変更しない。

1. **公開ページ URL（`publishedUrl`）の形式**。設計 §6.2（`docs/designs/api.md`）は `https://<hub-domain>/{handle}/{slug}` を想定するが、M3 thin slice で既存の web ルーティングはクエリパラメータベース（`/reading/?projectId=…`、`/projects/?projectId=…`、`REF:web/src/lib/links.ts`）である。公開フローが「第三者が URL を開いて本文を読める」ことを満たすため、`publishedUrl` は `{HUB_PUBLIC_BASE}/reading/?projectId={projectId}` として機械生成する。`{handle}/{slug}` のクリーン URL はクリーン URL ルーティングが導入された後続マイルストーンで追加する。`HUB_PUBLIC_BASE` は環境変数で設定し、既定はローカル開発用の `http://localhost:4321`。
2. **hub 登録（プロジェクトメタ）の保持**。設計 §6.2（`projects` テーブル・SQL マイグレーション）は M3 thin slice では未導入（`server/` crate に DB 依存が無い）。M3 ではインメモリのプロジェクト登録簿（`ProjectRegistry`、`Arc<RwLock<HashMap<projectId, ProjectRecord>>>`）でメタを保持し、読み取り（`GET /projects/{projectId}`・`/reading`）がポート経由で保管単位からコンテンツを読む。後続で DB 導入時に登録簿の実装を差し替えのみで移行できる（ポート経由で隔離）。zip は検証後に破棄し、恒久保存しない（仕様 §6.1）。
3. **セッションと利用者の紐付け**。公開フローでレスポンスの `ownerHandle` と保管単位名（`{handle}/{repo}`）が必要。既存の `Session` は利用者 ID のみ保持していたため、`Session` に `Identity`（ID・ハンドル・表示名）を保持させ、`POST /auth/github/callback` で交換済みの `Identity` を渡す。`require_auth` ミドルウェアが返すセッションからハンドルを取り出せる。
4. **multipart と zip 展開の自己完実装**。サンドボックスはオフラインビルドで、vendor に multipart（`multer`）／zip（`zip`／`flate2`）系の crate が未包含であり、crates.io へ到達できない。M3 では (a) multipart/form-data のパース（`Content-Type` の boundary ベース）と (b) ZIP の展開（手書きの DEFLATE 展開＋中央ディレクトリ／ローカルヘッダ解析）を純粋 Rust で自己実装し、外部 crate に依存しない。許可リスト（設計 §10.3）は展開時にストリームで検査する。
5. **novnow 軽量検証の具体的仕様**。設計 §2.1・§5.11 は「必須要素・文字コード・マニフェストの整合性」および「必須パス・UTF-8・`schema_version` を検査」と定めるが、具体的な必須パスは未定義だった。ユーザー判断により、軽量検証の判定は **novnow 本体の仕様（novnow リポジトリの `specifications/project.md` §4.2・§4.3）と同一** とし、hub 独自の必須要素を発明しない。必須ファイルは `project.toml`・`characters.md`・`words.md`・`materials/index.json`・`plots/all.cnov`、必須ディレクトリは `contents/`（空でも可）・`plots/`。`project.toml` は TOML として読め、`schema_version` が `2` または省略は OK、`2` より大きい版は拒否、TOML として読めない場合は拒否する。文字コードは文書ファイルの UTF-8 妥当性を検証し、不正バイトがあれば該当ファイルを列挙して拒否する。任意パス（`ideas.md`・`prompts/`・`agents/`・`exports/`・`.novnow/`）の欠落・未知ファイル・README は拒否理由にせず、不足ファイルを hub 側で自動生成して補うこともしない。本文 `.cnov` の構文診断までは軽量検証では行わない（M4 以降の novnow 診断へ委ねる）。いずれか失敗時は保管単位を作らず `400` で欠落・不正ファイルの一覧を返し、zip は検証後に破棄する（仕様 §6.1）。本判断は後続（M4 以降の本格化）で novnow 固有の検証ルールへ差し替え可能にする。
6. **PR #42 修正指示の判断（zip ディレクトリ entry・バイナリ・クリーンアップ・複数行 TOML・schema_version 検査範囲）**。PR #42（M3 公開フロー本体）に対する 5 件の修正指示に対応するための判断を定める。(a) **zip ディレクトリ entry の扱い**: 通常の zip（`zip -r` 相当）はディレクトリ entry（末尾 `/`、または Unix モードのディレクトリ）を含む。これをファイル化すると幽霊ファイルが生まれ、保管基盤のコミットで失敗（Git 422 等）する。ディレクトリ entry は展開結果の `files` ではなく `dirs` に分類し、必須ディレクトリ（`contents/`・`plots/`）の存在判定はファイルの有無とディレクトリ entry の存在の双方で行う。空の `contents/` はディレクトリ entry のみでも受理する。`__MACOSX/`・`.DS_Store` などのノイズ entry は展開結果から除外する。(b) **バイナリファイルのエンコーディング**: コミット時に UTF-8 として妥当ならテキスト、そうでない（バイナリ相当）は Base64 でコミットし、内容を壊さない（`from_utf8_lossy` で黙って文字化けさせない）。(c) **保管単位作成後の失敗時クリーンアップ**: 保管単位の作成後、コミット・公開範囲設定のいずれかで失敗した場合、中間状態を残さないために `delete_project_shell` で保管単位を削除する。削除自体が失敗した場合はその旨をエラーに含める。(d) **複数行 TOML 値**: `project.toml` のマルチライン値（配列・三重引用符のマルチライン文字列）を読めるように、`[`・`]` の深さと引用符状態を行間で追跡して平衡を検証する。不平衡なマルチライン配列・閉じていない文字列は TOML として読めず拒否する。(e) **`schema_version` 検査の範囲**: `schema_version` の検査は**トップレベルのキーのみ**とし、テーブル内の `schema_version` は検査対象外（省略扱い）とする。上記は `api/openapi.yaml` の契約を変更しない。検証は `real_zip_with_dir_entries_passes_full_verify` テスト（ディレクトリ entry 含む本物 zip を `import_zip` → `verify_snapshot` まで通す）で実行検証する。
7. **プロジェクト一覧・検索の軽量インデックス（カーソルページネーション・絞り込み範囲）**。M3 の残件「プロジェクト一覧・検索の最小実装」に対応するための判断を定める。(a) **軽量インデックスの実装**: DB を導入せず、インメモリ登録簿（`ProjectRegistry`）のスナップショットを走査して一覧・検索を実現する純粋関数モジュール（`project_index`）を置く。後続で DB 導入時は本モジュールの実装を差し替えのみで移行できる（判断 2 の延長）。(b) **カーソルページネーション**: 明示的な「次へ」に対応し、`nextCursor`（不透明文字列：並び順タグ＋最終項目の ID を base64url 化）で次のページを返す。総件数は返さない（設計 §4.2）。カーソルの並び順がリクエストと不一致、または項目が既に無い（期限切れ）場合は `400 validation_failed`。(c) **一覧のソート**: 契約の `sort`（`updated`・`created`・`derivatives`）に対応。`derivatives` は M3 では派生数が常に 0 のため更新日時で副排序する。公開作品のみ対象（`visibility == public`）。(d) **検索の絞り込み範囲**: 契約 `searchProjects` のクエリ（`q`・`license`・`tag`・`sort`）に対応。キーワードはタイトル・作者ハンドル・説明・タグを部分一致（関連度順）、ライセンスは列挙値、タグは部分一致。**作品種別の絞り込みは M3 では提供しない**（仕様 §4.2 に「作品の種別」とあるが、契約 `searchProjects` に種別を示すクエリ項目が無いため、契約にのみ準拠し対象外とする）。(e) **タグの保持**: `ProjectRecord` に `tags` を追加する。公開フローの multipart フォームにはタグ項目が無いため、M3 では空配列で登録し、後続でタグ入力が追加された際に populating する。上記は `api/openapi.yaml` の契約を変更しない。

8. **M4 コラボレーションポート実装判断（ProposalPort／IssuePort／AutomergePort／CheckStatusPort の GitHub 実装）**。M4 の最初の項目「4 ポートの GitHub 実装と契約テスト」において、仕様・設計・計画書のいずれを正とするかの判断と、実装上判断が必要だった点を定める。**権威の順位**: 実装が仕様・設計・計画書と矛盾した場合、**API 契約 `api/openapi.yaml` を正**とする（ユーザー制約「実装は API 契約にのみ準拠」による）。契約が明示しない運用詳細は設計 `docs/designs/m4.md` を正とし、設計も又持ち合わせない場合は仕様 `docs/specifications/m4.md` を正とする。本次では矛盾は発生しなかった。(a) **GitHub 概念の隠蔽**: GitHub の Pull Request を hub の `Proposal`、Issue を `Issue`、Check Runs を `CheckStatus`、Auto-merge を `AutomergeState` に写し、hub 側の型・ポート語彙のみを漏らさない。アダプター（`adapters/github`）が GitHub REST API を直接叩き、ポート経由でのみ扱う（差し替え可能）。(b) **承認数の算出**: 設計は「承認数」を定めるが取得元を特定しない。GitHub の **レビュー一覧 API（`/pulls/{n}/reviews`）の `state == "APPROVED"` 件数** を承認数とし、PR 自体の `review_count` は使わない（採用・要退回・コメントを区別できるため）。(c) **自動マージ状態の取得**: GitHub は予約状態を直接読む API を提供しない。`getAutomergeState` は PR の状態から評価し、予約済み（`Reserved`）を返す。予約・取消は GitHub の `PUT/DELETE /pulls/{n}/merge` で直接行い、`reserveAutomerge` の返り値は予約条件を反映した `Reserved` を返す。(d) **`requireNoConflicts` の扱い**: GitHub の自動マージは競合のある PR をマージしないため、`requireNoConflicts` は GitHub 側の仕組みで満たされる。明示的なフラグは存在せず、クライアントでは引数として保持するがリクエスト本体には含めない。(e) **インラインコメント（path・line）**: 契約 `Comment` は `path`・`line` を保持するが、GitHub のインラインレビューコメントは別のエンドポイント（`/pulls/{n}/comments`）を要する。M4 の thin slice では会話コメント（Issue コメント経由）のみ対応し、インラインコメントは**対象外**とする（型は保持し、実装は後続で差し替え）。(f) **差分の novnow 診断差分**: 契約 `ProposalDiff.novnowDiagnosticsDelta` は M4 thin slice では計算せず既定値（0）とする。診断は `CheckStatusPort` および M5 の diagnostics ジョブの責務とし、本次ではポート定義のみ整える。(g) **契約テストの手法**: ネットワーク非依存・決定性のため、ローカルに **mock GitHub API サーバー（axum）** を起動し、GitHub の応答形状→hub 型の写像と、アダプターが発するリクエスト（メソッド＋パス＋主要フィールド）が GitHub REST 契約に一致することを検証する。実機 GitHub へのアクセスは検証しない（トークン不要・冪等）。上記は `api/openapi.yaml` の契約を変更しない。検証は `cargo build`（警告 0）・`cargo test`（97 件成功、うち契約テスト 5 件）・`cargo clippy -D warnings` で実行検証する。

9. **M4 コラボレーションの HTTP ルート配線とフォローアップ修正判断**。M4 の 2 項目「4 ポートの HTTP ルート配線」と PR #44 レビュー由来のフォローアップ修正における判断を定める。**権威の順位**は判断 8 に準ず（**API 契約 `api/openapi.yaml` を正**）。(a) **CheckStatusPort と verify 系エンドポイントの対応**: 契約の `/projects/{projectId}/verify`（`verifyProject`）・`/verify/latest`（`getLatestVerification`）・`/diagnostics`（`runDiagnostics`）・`/jobs/{jobId}`（`getJob`）は **novnow 形式の妥当性検証**（`VerificationResult`：ok/errors/warnings）を返す機能であり、`CheckStatusPort`（GitHub の Check Runs → `Vec<CheckStatus>`）とは別責務で対応しない。よって CheckStatusPort を verify 系に配線せず、**配線は見送る**（判断として記録）。CheckStatusPort は内部（自動マージ条件の評価等）で使われるポートであり、本次では直接的な HTTP ルートを持たない。(b) **認可**: 契約で `security: []` の読み取り（変更提案・課題の一覧・詳細・差分、自動マージ状態の取得）は公開、書き込み系（作成・コメント・レビュー・マージ・クローズ・自動マージ予約・取消・課題の更新・クローズ）は既存の `require_auth` ミドルウェアで認証必須とする。読み取りは公開プロジェクトを基本とし、書き込みは認証を要する（設計 §8.1 と整合）。(c) **projectId → shell の解決**: ルートの `projectId` をインメモリ登録簿（`ProjectRegistry`）で `shell_id`（`{handle}/{repo}`）へ解決し、解決できなければ 404。ポートは `shell_id` で GitHub を操作する（GitHub の repo 名を API に漏らさない）。(d) **カーソルページネーション**: 一覧系（提案・課題・コメント）は契約の `cursor`／`limit` に対応。`limit` は既定 20・上限 100 で検証し、`cursor` は不透明文字列（オフセットの文字列表現）として扱う。範囲外・不正カーソルは 400。(e) **フォローアップ修正 (a) list_proposals の state 絞り込み**: PR #44 では GitHub の `state=all` を取得するだけで hub の `ProposalState` で絞り込んでおらず、要求 state と違う一覧を返し、closed にマージ済みが混入していた。修正後は GitHub 側で open/closed を一次取得し、**写像後の hub の `ProposalState` で二次絞り込み**する（approved/merged は GitHub 側で絞れないため写像後の state で絞る。closed 取得に混ざる merged は除外）。(f) **フォローアップ修正 (b) get_automerge_state の状態判定**: PR #44 では常に `Reserved` を返していた。修正後は PR の状態から **マージ済み→`merged`、クローズ済み（未マージ）→`canceled`、オープン/承認済み→`reserved`** を返す。(g) **ProposalState.Approved の判定**: 承認済みの定義は「オープンで承認数が要件（既定 1）以上」とし、`map_pr` で判定する。上記は `api/openapi.yaml` の契約を変更しない。検証は `cargo build`（警告 0）・`cargo test`（110 件成功、うちルート統合テスト 11 件・契約テスト 7 件）・`cargo clippy -D warnings` で実行検証する。

18. **M7 セキュリティレビュー（タスク1: フォールバック暗号化の鍵導出改善）の判断**。**権威の順位**は判断 8〜17 に準ず（**API 契約 `api/openapi.yaml` は不変**）。PR #54（判断 16）で導入したフォールバック暗号化ファイルの鍵導出を改善し、**パス単体からの鍵導出を不可能**にする。(a) **現状の問題**: 暗号化鍵は `SHA-256(app_data_dir パス ‖ 定数ソルト)` で、`app_data_dir` へアクセスできる者には導出可能な弱さがあった。平文よりはましだが、鍵導出設計としては弱い。(b) **候補の比較**: (a) インストール時にランダムな鍵を生成し、その鍵自体を OS キーチェーンに保管する方式、(b) マシン固有のエントロピー（machine-id 等）をソルトに使用する方式。(c) **選定: (b) マシン固有エントロピーを KDF に混ぜ込む方式**。**理由**: (a) は「キーチェーンが使えないフォールバック時」に鍵をキーチェーンに保管・取得できず、キーチェーン可用性の変化（例: Linux で dbus が起動→停止）で鍵が不一致となり既存暗号化ファイルを復号不能にするデータ損失リスクがある。(b) は決定的で一貫性があり、フォールバック時にも鍵を取得可能で、全プラットフォームでコンパイル・動作する。(d) **実装**: 鍵 = `SHA-256(app_data_dir パス ‖ マシン固有エントロピー ‖ 定数ソルト)`。マシン固有エントロピーは Linux は `/etc/machine-id`（代替 `/var/lib/dbus/machine-id`）、macOS は `ioreg` の `IOPlatformUUID`、Windows は `reg` の `MachineGuid` で取得し、最終手段でホスト名を用いる（`LazyLock` でプロセス内 1 回キャッシュ）。ソルトを `novnow-hub:session-key:v2` に更新（KDF 変更の明示）。導出関数 `derive_key` を純粋関数として分離し、単体テストで決定性・パス単体非導出・ディレクトリ依存を検証する。(e) **残存リスク**: マシン固有エントロピーへのアクセスと `app_data_dir` へのアクセスを**併せ持つ**攻撃者には鍵を導出可能。平文よりはましだが、OS キーチェーン（主back、セッション値をキーチェーンに直接保管）ほど強くない。本改善はフォールバック（キーチェーン不可時）の扱いを维持し、**平文には戻さない**。(f) **検証**: サンドボックス環境では src-tauri の `cargo test`／`cargo clippy` が実行不能（`tauri`／`aes-gcm`／`keyring` 等が vendored-sources 未収録・crates.io 到達不可。判断 15(f) の理由）のため、KDF の性質（決定性・パス単体非導出・ディレクトリ依存・32 バイト）を Python によるアルゴリズム再現で検証し、コンパイル検証は Desktop CI（3 プラットフォーム）の実行結果に委ねる。追加した `#[cfg(test)]` 単体テストは、完全な依存環境で `cargo test` されることを想定する。

--deny warnings` は **informational（unmaintained 等）の advisory も失敗扱い**するため、`chrono` の unmaintained 警告で CI が落ちた。**修正: `--deny warnings` を外し、既定の `cargo audit`
