# 設計書: M7 運用・品質・OSS 公開準備

本書は `REF:docs/specifications/m7.md` の各節に対応する実装設計を述べる。見出しは仕様書と一致させ、各 `###` 節の冒頭に実装状態を置く。契約の唯一の正は `REF:api/openapi.yaml`（OpenAPI 3.1）であり、M7 は主に運用・品質・公開準備（デプロイ・監視・セキュリティ・ドキュメント・性能検証）の機能であるため、API 契約への変更は不要である。GitHub へのアクセスはアダプター層の背後に隠され、API 契約・フロントエンド・利用者体験には GitHub の概念を漏らさない。

## 1. 目的とスコープ

### 1.1 目的とスコープ

状態: 未実装・実装計画済み（REF:docs/plans.md#m7-ops）

M7 は novnow-hub を OSS として一般公開できる状態にする。バックエンドは API 契約 `REF:api/openapi.yaml` にのみ準拠し、デプロイ・監視・セキュリティ・ドキュメント・性能検証を整備する。

## 2. 本番デプロイとインフラ運用

### 2.1 本番デプロイ

状態: 実装完了（REF:docs/plans.md#m7-ops）

本番デプロイは Workers + D1 を既定とし、VPS + Docker を代替構成とする。デプロイパイプラインにより、コード変更を本番環境に安全に適用できる。デプロイは GitHub Actions 等の CI/CD を用い、本番環境への適用は手動承認または自動デプロイのいずれかを選択できる。

**実装**: デプロイ資材とパイプラインを整備。既定構成（Workers + D1）は `REF:deploy/workers-d1/wrangler.toml` と `REF:deploy/workers-d1/DEPLOY.md`、代替構成（VPS + Docker）は `REF:deploy/vps-docker/Dockerfile`・`REF:deploy/vps-docker/docker-compose.yml`・`REF:deploy/vps-docker/nginx/novnow-hub.conf` と `REF:deploy/vps-docker/DEPLOY.md` を用意する。デプロイパイプラインは `REF:.github/workflows/deploy.yml`（web とサーバーのビルド → 手動承認ゲート → Workers デプロイ）。デプロイ先のアカウント・ドメイン・Secrets の有効化はアカウント側の操作が必要と明記（無理に実行しない）。秘密はリポジトリに載せずプレースホルダで対応。判断は `REF:docs/handoff.md` 判断 21・22。

### 2.2 外形監視

状態: 実装完了（REF:docs/plans.md#m7-ops）

公開ページおよび hub API の外形監視を行う。監視は定期的にエンドポイントにリクエストを送信し、応答コードと応答時間を検知する。異常時はアラートを発報する。

**実装**: ヘルスチェックスクリプト `REF:deploy/monitoring/healthcheck.sh`（公開ページと `GET /api/v1/meta` の外形を 200 で検証）と手順 `REF:deploy/monitoring/MONITORING.md` を整備。定期実行は GitHub Actions のスケジュールワークフロー `REF:.github/workflows/monitoring.yml`（既定 5 分間隔、異常時は Issue 作成）。監視範囲は「応答しているか」の外形のみとし、内部のパフォーマンス計測は §6 と区別する。判断は `REF:docs/handoff.md` 判断 23。

### 2.3 バックアップと鍵ローテーション

状態: 実装完了（REF:docs/plans.md#m7-ops）

重要データ（D1 データベース等）のバックアップ手順を定義し、定期的に実行する。暗号鍵・トークン等の秘密情報は定期的にローテーションし、古い鍵は失効させる。

**実装**: バックアップスクリプト `REF:deploy/backup/backup.sh` と手順 `REF:deploy/backup/BACKUP.md`、鍵ローテーションスクリプト `REF:deploy/backup/rotate-secrets.sh` と手順 `REF:deploy/backup/ROTATION.md` を整備。バックアップ対象はデプロイ資材と各構成のデータ基盤（D1 / Docker ボリューム）に絞り、秘密はリポジトリに載せずプレースホルダで対応する。実際のバックアップ・ローテーションの実行はアカウント側の操作が必要と明記。判断は `REF:docs/handoff.md` 判断 24・25。

## 3. CI の拡張と品質ゲート

### 3.1 契約互換性検査

状態: 実装完了（REF:docs/plans.md#m7-ops）

OpenAPI 契約の互換性検査（oasdiff 相当）を CI に組み込む。新版と旧版のスキーマを比較し、破壊的変更（必須化・改名・削除等）を検出して CI を落とす。

**実装**: oasdiff の代わりに独自の差分チェックスクリプト `docs/script/check-openapi-compat.py` を実装し、`contract` ジョブで PR の base と head の `api/openapi.yaml` を比較して破壊的変更（パス削除・operation 削除・operationId 変更・必須フィールド削除・型変更・enum 値削除・レスポンスコード削除・security 厳格化・securityScheme 削除）を検出する。破壊的変更があれば CI 失敗、openapi.yaml 未変更時はスキップする。判断は `REF:docs/handoff.md` 判断 19。

### 3.2 脆弱性検査とカバレッジゲート

状態: 実装完了（REF:docs/plans.md#m7-ops）

`cargo audit`（Rust 依存）および `npm audit`（Node.js 依存）による脆弱性検査を CI に組み込む。テストカバレッジゲートにより、品質を担保する。

**実装**: `rust` ジョブに `cargo audit`（真の脆弱性のみ失敗・informational は報告）を追加。`lint` ジョブに `npm audit --omit=dev`（production 依存のみ失敗）を追加。カバレッジゲートは `coverage` ジョブで server（`cargo llvm-cov`）と web（Vitest v8、`web/vitest.config.ts` の `thresholds`）を計測する。ゲート方針と下限設定の判断は `REF:docs/handoff.md` 判断 19。

## 4. セキュリティレビューと依存ライセンス

### 4.1 セキュリティレビュー

状態: 実装中（タスク1: セッション情報（トークン）の暗号化保管を実装。zip 取込・CSP・権限判定のレビューは未実施・REF:docs/plans.md#m7-ops）

zip 取込・CSP・トークン暗号化・権限判定についてセキュリティレビューを行う。zip 内のパス traversal（`../` 等）、CSRF、XSS、クリックジャッキングへの対策をレビュー対象とする。トークンは暗号化して保管し、権限判定により非公開対象へのアクセスを制限する。

**進捗（第1弾）**: トークン暗号化保管を実装。`src-tauri/src/lib.rs` の `SecureStorage` は OS キーチェーン（`keyring` v3）を主backとし、利用不可環境では AES-256-GCM 暗号化ファイルへフォールバックして平文露出を排除する（`REF:docs/handoff.md` 判断 16）。フォールバック暗号化の鍵導出はマシン固有エントロピー（machine-id 等）を混ぜ込み、パス単体からの鍵導出を防止する（`REF:docs/handoff.md` 判断 18）。インストーラ署名は M6 設計 §5 の続きとして対応（`REF:docs/handoff.md` 判断 17）。平文セッション保管の問題は Issue #53 にまとめて管理する。

### 4.2 依存ライセンスの棚卸し

状態: 未実装・実装計画済み（REF:docs/plans.md#m7-ops）

使用する依存ライブラリのライセンスを棚卸し、OSS として公開するにあたって問題がないかを確認する。ライセンス互換性を確認し、必要に応じて代替ライブラリを検討する。

## 7. 非機能要件

### 7.1 セキュリティ

状態: 未実装・実装計画済み（REF:docs/plans.md#m7-ops）

zip 取込のパス traversal・CSRF・XSS・クリックジャッキングへの対策を行う。トークン暗号化により秘密情報を保護する。権限判定により非公開対象へのアクセスを制限する。

### 7.2 性能と可用性

状態: 未実装・実装計画済み（REF:docs/plans.md#m7-ops）

公開ページの初回表示は国内モバイル回線で 2 秒以内の Largest Contentful Paint を目標とする。hub API の読み取り系エンドポイントのサーバ処理時間は p95 で 200 ミリ秒以内を目標とする。月間可用性目標は 99.5% とする。

### 7.3 コスト制約

状態: 未実装・実装計画済み（REF:docs/plans.md#m7-ops）

共有インスタンスの運用コストは、GitHub とサーバーレス無料枠＋最小限の有償枠のみで、月額数千円以下を目安とする。定時実行（cron）の頻度・実行時間に上限を設け、従量課金の暴走を防ぐ。
