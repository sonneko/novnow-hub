# 設計書: M5 novnow 特化機能（セットアップ URL・派生ツリー・診断）

本書は `REF:docs/specifications/m5.md` の各節に対応する実装設計を述べる。見出しは仕様書と一致させ、各 `###` 節の冒頭に実装状態を置く。契約の唯一の正は `REF:api/openapi.yaml`（OpenAPI 3.1）であり、M5 に必要なエンドポイント（`/projects/{projectId}/derivatives`、`/projects/{projectId}/derive`、`/projects/{projectId}/diagnostics`、`/jobs/{jobId}`、`/projects/{projectId}/exports`、`/projects/{projectId}/verify`、`/projects/{projectId}/verify/latest`、`/setup/resolve`、`/projects/{projectId}/setup`）は既に契約に定義済みのため、契約ファイルへの変更は不要である。GitHub へのアクセスは DerivationPort／JobPort 等のアダプター層の背後に隠され、API 契約・フロントエンド・利用者体験には GitHub の概念を漏らさない。

---

## 1. 目的とスコープ

### 1.1 目的とスコープ

状態: 未実装・実装計画済み（REF:docs/plans.md#m5-novnow-features）

M5 は Phase 1 の novnow 特化機能を実装する。バックエンドは API 契約 `REF:api/openapi.yaml` にのみ準拠し、派生・診断・ジョブの外部基盤連携は各ポートの GitHub アダプターまたは hub 管理ストアで実現する。Phase 2 ではアダプター差し替えのみで自前バックエンドへ移行でき、API 契約とクライアントは変更しない。

## 2. 派生ツリーと派生レコード

### 2.1 派生ツリー UI（/derivatives）

状態: 実装完了（REF:web/src/components/pages/DerivativesPage.svelte, REF:web/src/components/pages/ProjectPage.svelte, REF:api/openapi.yaml）

派生ツリー UI は `/derivatives` ルートで提供され、プロジェクトページの「派生」タブとして統合する。直接の子作品・孫以降・兄弟作品を木構造で表示し、各ノードはタイトル・作者・更新日・派生可否を示す。派生元の連鎖を保持し、原作者への通知は §6 の通知基盤でファンアウトする。

### 2.2 派生レコードと派生元連携

状態: 実装完了（REF:server/src/ports.rs, REF:server/src/adapters/github/derivation.rs, REF:server/src/routes/derivatives.rs, REF:api/openapi.yaml）

派生レコードは `DerivationPort`（`createDerivative`、`listDerivatives`、`getDerivative`、`getDerivationTree`）で操作する。Phase 1 の `DerivationPort` 実装は GitHub の Fork を代理操作するアダプターで、派生の実体は GitHub リポジトリのコピーとし、派生元との対応関係は hub 側で記録する。派生時にライセンス継承の確認・作品名の既定値・説明の初期値を提示する。派生作品の初回公開時も novnow 形式の検証（§3.1 相当）を通す。

## 3. セットアップ URL

### 3.1 セットアップ URL 発行（/projects/{id}/setup）

状態: 実装完了（REF:web/src/components/pages/ProjectPage.svelte, REF:api/openapi.yaml）

セットアップ URL 発行は `GET /projects/{projectId}/setup` エンドポイントで処理し、匿名可とする。レスポンスは `SetupInfo` スキーマに従い、プロジェクト識別子・slug・スナップショットバージョン・取得元情報（kind/url/ref）・novnow 最小バージョン・表示ヒントを含む。`acquisition.url` は認証不要の公開 tarball（archive 相当）を既定とする。web 側では ProjectPage でこのエンドポイントを呼び出し、セットアップ URL をクリップボードにコピーする導線を提供する。PR #12 で実装済み。

### 3.2 セットアップ URL 解決（/setup/resolve）

状態: 実装完了（REF:web/src/pages/setup/resolve.astro, REF:web/src/components/pages/SetupResolvePage.svelte, REF:api/openapi.yaml）

セットアップ URL 解決は `GET /setup/resolve?u=…` エンドポイントで処理し、匿名可とする。公開ページのセットアップ URL を解釈し、取得元と手順情報を返す。アプリが公開 URL から出発できるようにするため、認証不要の公開 tarball を既定とし、私設の場合は短期失効トークン付き URL を発行する。いずれの場合も hub のセッションをアプリへ渡さない。

### 3.3 novnow アプリ側ハンドラ仕様

状態: 実装完了（REF:docs/specifications/m5.md, REF:web/src/components/pages/ProjectPage.svelte, REF:api/openapi.yaml）

novnow アプリ（デスクトップ／ブラウザ）がセットアップ URL を解釈し、作品の取得 → ローカルへの配置 → novnow プロジェクトとしての初期化検証 → エディタを開くを自動で行う。デスクトップ版は OS のカスタムスキーム（`novnow://`）で、ブラウザ版は通常の URL でセットアップ URL を受け取る。いずれも同じ URL の意味を持つ。セットアップに失敗した場合は、失敗工程と手動での取得方法を表示する。

実装（hub 側）: novnow アプリ自体は本リポジトリ外のため、hub 側の責務はセットアップ URL の発行・解決と、アプリが受信後に参照する取得元情報の提供である。`GET /projects/{projectId}/setup`（§3.1）が `SetupInfo`（取得元 kind/url/ref・novnow 最小バージョン・表示ヒント）を返し、web 側の `ProjectPage.svelte` はブラウザ用の通常 URL（`setupResolveHref` ベースの `browserSetupUrl`）の表示・クリップボードコピー導線、および手動取得用の `acquisition.url` 導線を提供する。デスクトップ版のカスタムスキーム受信（`novnow://`）は M6 の Tauri 実装（`handle_setup_url`）が担い、受信後は Web アプリの `/setup/resolve/?u=<url>` へ遷移させる。失敗時の失敗工程表示と手動取得導線はアプリ側の責務だが、hub は取得元情報と公開 URL を安定的に提供することで、アプリが失敗工程と手動取得手順を表示できることを支える。契約の変更は不要。

## 4. novnow 診断・エクスポート

### 4.1 非同期ジョブ基盤（JobPort）

状態: 実装完了（REF:server/src/ports.rs, REF:server/src/jobs.rs, REF:server/src/routes/jobs.rs, REF:api/openapi.yaml）

novnow 診断・エクスポートは `JobPort`（`createJob`、`getJob`、`listJobs`、`cancelJob`）で操作する。ジョブは非同期に実行され、完了を通知で知らせる。hub 自身は novnow 本体の全機能を再実装しない。重い処理はキュー化し、同時実行数を制限する。

実装: `JobPort` は `server/src/ports.rs` に定義し、`server/src/jobs.rs` の `JobManager` が実装する。ジョブは起票時に `tokio::spawn` でバックグラウンドタスクに委譲し、`JOB_CONCURRENCY_LIMIT`（定数、上限 2）で同時実行数を制限する。完了は既存通知基盤（`NotificationKind::JobFinished`）で通知する。失敗時は状態を `failed` として理由を結果に残し、サーバーログにも残す。キャンセルはポート語彙で `Cancelled` を持つが、契約 `Job.status` の列挙に `cancelled` は無いため API 境界では `failed`（理由「キャンセルされました」）に写像する（判断は `docs/handoff.md` §4 に記録）。

### 4.2 診断の実行環境

状態: 実装完了（REF:server/src/jobs.rs, REF:server/src/verify.rs, REF:docs/handoff.md）

診断の実行環境は、novnow の WASM 実行を既定とし、利用できない場合は GitHub Actions 上の novnow CLI をフォールバックとする。診断結果は「点検」タブに表示できる。GitHub Actions へのアクセスは JobPort の GitHub アダプターの背後に隠す。

実装（Phase 1）: 本段階では novnow の WASM モジュールがベンダー未収録・オフラインのため WASM 実行は現実的でない。代替として既存の M3 軽量検証（`verify::verify_snapshot`、novnow 形式の必須ファイル・UTF-8・マニフェスト整合性検査）を診断の最小実装として再利用し、GitHub の概念は `JobContentPort`（`ContentPort` 実装の背後に隠す）の背後に隠す。hub は novnow 本体の全機能を再実装しない。選択理由と根拠は `docs/handoff.md` §4 に記録。

### 4.3 エクスポート

状態: 実装完了（REF:server/src/jobs.rs, REF:server/src/routes/jobs.rs, REF:api/openapi.yaml）

エクスポートは `POST /projects/{projectId}/exports` エンドポイントで処理し、本文のエクスポート（注釈除去済みテキスト／Markdown）を生成する。生成物はダウンロードまたは変更提案に添付できる。

実装（Phase 1）: エクスポートジョブは `JobKind::Export` として起票し、`JobRunner` がプロジェクトの文書ファイルを集約して注釈を除いた本文を生成する。出力形式は契約 `createExport` の `format`（`txt` / `markdown`）に従う。

## 5. 変更提案差分への novnow 診断差分

### 5.1 診断差分の付与

状態: 実装完了（REF:server/src/adapters/github/mod.rs, REF:server/src/ports.rs, REF:api/openapi.yaml）

変更提案の差分には、`CheckStatusPort` による novnow 診断結果（新たに混入した誤りや解消された誤り）を併せて表示する。診断結果は変更提案の必須チェックとして利用でき、診断エラーがある場合は取り込みをブロックするか警告を表示する。診断結果は非同期ジョブとして実行され、完了を通知で知らせる（§4.1）。

実装: 変更提案の差分取得（`diff_proposal`、GitHub アダプター）で、PR の base  ref と head  ref それぞれのチェックランを `CheckStatusPort::get_check_status` で取得し、**名前が `novnow` を含み状態が Failure のチェック**を比較して差分を算出する。head にあって base に無いものを `introduced`（新たに混入した誤り）、base にあって head に無いものを `resolved`（解消された誤り）として `ProposalDiff.novnowDiagnosticsDelta` に設定する（空リストは差分 0）。GitHub の概念（Check Run・ref）はアダプター層の背後に隠し、契約の `novnowDiagnosticsDelta` のみを API に漏らす。フロントエンド（`ProposalDetailPage.svelte`）は既存の `diff.novnowDiagnosticsDelta` 表示を流用する。契約の変更は不要。

## 6. 公開前検証の本格化

### 6.1 novnow check 相当の診断を必須チェックに連動

状態: 実装完了（REF:server/src/verification.rs, REF:server/src/routes/verify.rs, REF:server/src/lib.rs, REF:api/openapi.yaml）

公開前の novnow 点検（診断エラー 0 件）を変更提案の必須チェックとして登録できる。チェック結果は変更提案に表示され、自動マージの条件に使える。重いチェックは非同期に行い、提案をブロックしすぎない。

実装: 公開前検証は `VerificationService`（`server/src/verification.rs`）が担う。`JobContentPort`（`ContentPort` 実装の背後に隠す）経由でプロジェクトのスナップショットを再帰的に読み取り、M3 の軽量検証（`verify::verify_snapshot`）を同期で実行し、結果を `DiagnosticsResult`（ok/errors/warnings/checkedAt）として `VerificationStore` にプロジェクト別に保持する。HTTP ルートは `POST /projects/{projectId}/verify`（認証必須、契約 `verifyProject`）と `GET /projects/{projectId}/verify/latest`（匿名可、契約 `getLatestVerification`）を `build_router` に配線し、`routes/verify.rs` が契約の `VerificationResult` を返す。プロジェクト未登録は 404、未検証の `verify/latest` も 404 とする。重いスナップショット読み取りは同期だが、変更提案の閲覧をブロックしないため、提案フロー上は直近結果（`verify/latest`）を参照する設計とする。M4 判断 9 で配線見送りとされた verify 系を本タスクで配線した理由は `docs/handoff.md` §4 判断 20 に記録する。契約の変更は不要。

## 7. 非機能要件

### 7.1 セキュリティ

状態: 未実装・実装計画済み（REF:docs/plans.md#m5-novnow-features）

Webhook 受信には署名検証を行い、なりすましを防ぐ。変更提案・課題・チャットの内容を認可を経ずに返さず、非公開プロジェクトに関わるイベントは関係者以外に通知しない。

### 7.2 性能と可用性

状態: 未実装・実装計画済み（REF:docs/plans.md#m5-novnow-features）

通知ファンアウトと書き込み系 API はキュー化し、同時実行数を制限する。診断・エクスポートなどの重い処理は非同期に行い、閲覧をブロックしない。
