# 設計書: M4 コラボレーション（変更提案・課題・自動マージ・チャット・通知）

本書は `REF:docs/specifications/m4.md` の各節に対応する実装設計を述べる。見出しは仕様書と一致させ、各 `###` 節の冒頭に実装状態を置く。契約の唯一の正は `REF:api/openapi.yaml`（OpenAPI 3.1）であり、M4 に必要なエンドポイント（`/projects/{projectId}/proposals`、`/projects/{projectId}/issues`、`/projects/{projectId}/chat/channels`、`/notifications` 等）は既に契約に定義済みのため、契約ファイルへの変更は不要である。GitHub へのアクセスはアダプター層（ProposalPort／IssuePort／AutomergePort／CheckStatusPort／ChatPort）の背後に隠され、API 契約・フロントエンド・利用者体験には GitHub の概念を漏らさない。

---

## 1. 目的とスコープ

### 1.1 目的とスコープ

状態: 未実装・実装計画済み（REF:docs/plans.md#m4-collaboration）

M4 は Phase 1 のコラボレーション機能を実装する。バックエンドは API 契約 `REF:api/openapi.yaml` にのみ準拠し、保管・変更提案・課題・チャット・通知の外部基盤連携は各ポートの GitHub アダプターまたは hub 管理ストアで実現する。Phase 2 ではアダプター差し替えのみで自前バックエンドへ移行でき、API 契約とクライアントは変更しない。

---

## 2. 変更提案（プロポーザル）

### 2.1 変更提案の作成とレビュー

状態: 未実装・実装計画済み（REF:docs/plans.md#m4-collaboration）

変更提案は `ProposalPort`（`createProposal`、`getProposal`、`listProposals`、`reviewProposal`）で操作する。Phase 1 の `ProposalPort` 実装は GitHub の Pull Request を代理操作するアダプターで、提案の実体と会話は GitHub 側に保存し、hub は表示と操作のファサードを提供する。差分は本文テキスト単位で算出し、インラインコメント・全体コメントをサポートする。レビュー状態（オープン／承認済み／取り込み済み／却下）は hub の語彙で管理し、アダプター経由で GitHub のレビュー状態と同期する。

### 2.2 差分と診断の表示

状態: 未実装・実装計画済み（REF:docs/plans.md#m4-collaboration）

差分表示は `CheckStatusPort` による診断結果（novnow check 相当）を差分に添える。診断エラーがある場合は取り込みをブロックするか警告を表示する。診断結果は非同期ジョブとして実行され、完了を通知で知らせる（§6）。

---

## 3. 課題（イシュー）

### 3.1 課題の管理

状態: 未実装・実装計画済み（REF:docs/plans.md#m4-collaboration）

課題は `IssuePort`（`createIssue`、`getIssue`、`listIssues`、`closeIssue`）で操作する。Phase 1 の `IssuePort` 実装は GitHub の Issue を代理操作するアダプターで、課題の実体と会話は GitHub 側に保存する。課題テンプレートとラベルは hub の語彙で定義し、アダプター経由で GitHub のラベルと同期する。課題から変更提案への紐付け（この提案は課題 X を解決する）は hub 側で記録し、関連づけて閲覧できる。

---

## 4. 自動マージ

### 4.1 自動マージの予約と状態表示

状態: 未実装・実装計画済み（REF:docs/plans.md#m4-collaboration）

自動マージは `AutomergePort`（`reserveAutomerge`、`cancelAutomerge`、`getAutomergeStatus`）で操作する。条件は必要な承認数（既定 1）、必須チェック（`CheckStatusPort` の診断エラー 0 件等）の通過、競合がないことの組合せで指定する。Phase 1 の実行主体は GitHub の自動マージ機構、または hub の定期評価（cron）を用いる。状態（予約済み／評価中／取り込み済み／条件未達／競合で失敗）は提案画面に表示し、発火時には誰が操作したかを含めて記録に残す。

---

## 5. チャット

### 5.1 チャットルームとメッセージ

状態: 未実装・実装計画済み（REF:docs/plans.md#m4-collaboration）

チャットは `ChatPort`（`createRoom`、`listRooms`、`sendMessage`、`listMessages`、`editMessage`、`deleteMessage`）で操作する。Phase 1 の `ChatPort` 実装は hub 管理の軽量ストア（組込 DB や KV ストア等）に保存し、外部基盤には保存しない。メッセージは時系列表示・未読バッジ・編集・論理削除をサポートし、メンション（@表示名）で通知を送る。Phase 1 は短間隔ポーリングでメッセージを取得する。UI はメッセージ一覧・入力フォーム・ルーム切替を備える。

---

## 6. 通知

### 6.1 通知センターと未読バッジ

状態: 未実装・実装計画済み（REF:docs/plans.md#m4-collaboration）

通知は hub 管理ストアに保存され、通知センターで集約表示する。対象イベントは派生作品の作成・変更提案・その承認/取り込み/自動マージ結果・課題の作成/コメント・チャットのメンション等である。未読/既読/全既読・種別フィルタ・ページネーションをサポートし、未読バッジで数を表示する。

### 6.2 通知のファンアウト

状態: 未実装・実装計画済み（REF:docs/plans.md#m4-collaboration）

ドメインイベント発生時に関係者へ通知をファンアウトする。ファンアウトはキュー化し、同時実行数を制限する。通知チャネルは既定で hub 内のみとし、メール・Web Push 等はオプトインで将来拡張できる。

---

## 7. GitHub Webhook 受信による公開ページ再生成

### 7.1 Webhook 受信とキャッシュ失効

状態: 未実装・実装計画済み（REF:docs/plans.md#m4-collaboration）

Webhook 受信エンドポイント（外部基盤からのプッシュ）で署名検証を行い、なりすましを防ぐ。検証後のイベントに応じて対象プロジェクトの公開ページを再生成し、CDN 等のキャッシュを失効させる。再生成は非同期ジョブとして実行し、閲覧をブロックしない。処理結果はログに残り、失敗時はリトライまたは手動再実行の導線を提供する。Webhook の処理はアダプター層の背後にあり、API 契約・フロントエンドには GitHub の概念を漏らさない。

---

## 8. 非機能要件

### 8.1 セキュリティ

状態: 未実装・実装計画済み（REF:docs/plans.md#m4-collaboration）

Webhook 受信には署名検証を行う。変更提案・課題・チャットの内容を認可を経ずに返さず、非公開プロジェクトに関わるイベントは関係者以外に通知しない。

### 8.2 性能と可用性

状態: 未実装・実装計画済み（REF:docs/plans.md#m4-collaboration）

通知ファンアウトと書き込み系 API はキュー化し、同時実行数を制限する。Webhook 受信による再生成は非同期に行う。
