# 設計書: M6 マルチプラットフォーム（Tauri・PWA）

本書は `REF:docs/specifications/m6.md` の各節に対応する実装設計を述べる。見出しは仕様書と一致させ、各 `###` 節の冒頭に実装状態を置く。契約の唯一の正は `REF:api/openapi.yaml`（OpenAPI 3.1）であり、M6 は主にクライアントサイド（Tauri v2 デスクトップビルド・PWA 化・セッション保管・インストーラ署名）の機能であるため、API 契約への変更は不要である。GitHub へのアクセスはアダプター層の背後に隠され、API 契約・フロントエンド・利用者体験には GitHub の概念を漏らさない。

---

## 1. 目的とスコープ

### 1.1 目的とスコープ

状態: 実装完了

M6 は Phase 1 のマルチプラットフォーム対応を実装する。Web アプリ（Astro + Svelte + TypeScript）と同一のコードベースを Tauri v2 でデスクトップアプリとしてパッケージングし、PWA 化によるオフライン閲覧を実現する。Phase 2 ではアダプター差し替えのみで自前バックエンドへ移行でき、API 契約とクライアントは変更しない。

---

## 2. Tauri v2 デスクトップビルド

### 2.1 デスクトップアプリの提供

状態: 実装完了

Tauri v2 により、Web アプリと同一のコードベースを Windows／macOS／Linux 向けデスクトップアプリとしてパッケージングする。見た目と操作は Web 版と共通とし、Tauri の WebView を使用してレンダリングする。

### 2.2 配布パイプライン

状態: 実装完了

デスクトップアプリのビルドを CI パイプラインで自動化する。各プラットフォーム向けにビルド成果物を生成し、配布可能な形式で出力する。ビルド成果物の署名・配布は §5 と連携する。

---

## 3. PWA 化

### 3.1 PWA マニフェストとオフラインシェル

状態: 実装完了

PWA マニフェスト（manifest.json）を提供し、ブラウザからアプリとしてインストールできるようにする。オフラインシェルにより、ネットワークが不安定な環境でもアプリのシェル部分を表示できる。Service Worker により静的リソースをキャッシュする。

### 3.2 読者ビューのオフライン閲覧

状態: 実装完了（読者ビュー本文の CacheStorage 保存とオフライン表示は M3 の事前描画と ETag キャッシュ（PR #19）の既存仕組みを再利用。PWA のマニフェスト・Service Worker オフラインシェルを実装し、インストール済みアプリとしてのオフライン閲覧経路を完成）

読者ビュー（公開ページの本文）をオフラインで閲覧できる。キャッシュ戦略により、既に読んだ公開ページの本文をオフラインでも表示できる。キャッシュキーはプロジェクト識別子と更新 ETag で構成する。なお、このキャッシュ戦略（プロジェクト識別子と更新 ETag をキーとする読者ビュー本文の CacheStorage 保存とオフライン表示）は M3 の事前描画と ETag キャッシュ（PR #19）で先行実装済みであり、M6 では PWA のマニフェスト・オフラインシェル（Service Worker）を整え、インストール済みアプリとしてのオフライン閲覧経路を完成させる。

---

## 4. セッション保管とセットアップ URL 受信

### 4.1 Tauri secure storage へのセッション保管

状態: 実装完了

デスクトップアプリでは、セッション情報（アクセストークン・更新トークン）を Tauri secure storage（macOS Keychain / Windows Credential Manager / Linux Secret Service 等）に保管する。ブラウザ版とは異なり、メモリのみに依存せず、アプリ再起動後もセッションを維持できる。セッション情報は平文で露出しない。

### 4.2 カスタムスキームでのセットアップ URL 受信

状態: 実装完了

デスクトップアプリは OS のカスタムスキームでセットアップ URL を受信し、作品の取得 → ローカルへの配置 → novnow プロジェクトとしての初期化検証 → エディタを開くを自動で行う。URL ひとつでセットアップ済みの作品をアプリで開けること。URL にはプロジェクト識別情報のみを含み、認証情報や個人情報を含まない。

---

## 5. インストーラ署名およびストア配布

### 5.1 インストーラ署名またはストア配布の方式

状態: 実装完了

デスクトップアプリのインストーラに署名を付与するか、ストア配布の方式を決定し実装する。署名により、ユーザーはインストーラの出所を検証でき、改ざんを防ぐ。

### 5.2 配布方式の決定

状態: 実装完了

Phase 1 では、インストーラ署名またはストア配布のいずれかを既定の配布方式とし、利用者が安全にデスクトップアプリをインストールできるようにする。方式の決定は M7 の運用・公開準備と整合させる。

既定の配布方式は「CI で生成した未署名インストーラ」とし、署名は M7 の運用・公開準備として別途対応する。署名証明書がこの開発環境で用意できないため（理由の詳細は `REF:docs/handoff.md` §4 判断 15 を参照）。デスクトップビルドの検証は CI のデスクトップパイプライン（`REF:.github/workflows/desktop.yml`、Linux/Win/macOS）で行う。サンドボックス環境では Tauri のバイナリビルドを実行できない（crates.io 到達不可・`tauri`/`iota_stronghold` 未ベンダー・webkit2gtk/gtk3 未導入）ため、検証は CI の実行結果に委ねる。

**CI ビルド失敗の原因特定と修正（PR #52 フォローアップ）**。初回の Desktop ワークフローが 3 プラットフォーム全て「Build desktop app (Tauri, unsigned)」で失敗した。ジョブログは確認できなかったためソース・ドキュメントで原因を特定し修正した。(a) **`stronghold` クレートの誤用**: `Cargo.toml` に `stronghold = "2"` を指定していたが、crates.io の `stronghold` は IOTA Stronghold とは無関係の別クレート（最終版 0.2.1、バージョン 2 は存在しない）であり、依存解決で失敗していた。IOTA Stronghold の実クレートは **`iota_stronghold`**（最新 2.1.0）であるため、`iota_stronghold = "2"` に修正。(b) **`Stronghold` の API 不整合**: `src-tauri/src/lib.rs` が `Stronghold::read_from/write_to/delete` を使っていたが、`iota_stronghold` 2.x の `Stronghold` にはこれらのメソッドは存在せず、`store()` 経由の `Store`（同期 API: `insert`/`get`/`delete`）を使う設計に修正。(c) **`register_uri_scheme_protocol` の返り値**: Tauri v2 ではハンドラ閉関数が **`http::Response`** を返す（`Result` ではない）。`Ok(())` を返していたのは型エラーであったため、空の 200 応答を返すよう修正し、`http = "1"` を依存に追加（tauri は `http` を再エクスポートしない）。(d) **`custom-protocol` フィーチャー**: Tauri v2 では `tauri/custom-protocol` は不要となり無視されるため、未定義に整理した。(e) **アイコン一式**: `bundle.icon` に `icons/icon.png` のみを登録していたため Windows ビルドが `icon.ico` 不在で失敗する。`tauri icon` で Tauri 2 標準のアイコン一式（`icon.ico`/`icon.icns`/各 PNG）を生成し、`bundle.icon` に `32x32.png`・`128x128.png`・`128x128@2x.png`・`icon.icns`・`icon.ico` を登録した。(f) **stronghold の排除と keyring への切り替え**: 上記修正後も Desktop CI は全 3 プラットフォーム「Build desktop app」で失敗した（ジョブログ取得不可のためソース検証で対応）。要件は「secure storage（OS キーチェーン）へのセッション保管・平文露出禁止」であり、IOTA Stronghold（`iota_stronghold`）は依存関係が重く全プラットフォームでコンパイル失敗したため必須でない。OS のキーチェーンを直接利用する **`keyring = "2"`** に切り替え（Linux は `libsecret-1-dev` を CI に導入）、`SecureStorage` を `Entry`（service `novnow-hub` / account = セッションキー）経由の `get_password`/`set_password`/`delete_password` に書き換え、同要件を満たす。修正の正しさは CI の Desktop ワークフロー再実行で検証する。

## 6. 非機能要件

### 6.1 セキュリティ

状態: 実装完了

セッション情報はクライアント側の安全なストレージに保管し、平文で露出しない。インストーラ署名により改ざんを防ぐ。GitHub へのアクセスはアダプター層の背後に隠し、API 契約・フロントエンド・利用者体験には GitHub の概念を漏らさない。

### 6.2 性能と可用性

状態: 実装完了

デスクトップアプリの起動とオフライン閲覧は、ネットワークに依存せず動作する。PWA のキャッシュ戦略により、読者ビューのオフライン閲覧を実現する。
