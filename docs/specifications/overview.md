# 仕様書: 概要（Overview）

本書は novnow-hub の設計原則・用語・ユーザーから見える振る舞いの全体像を定義する。API の詳細は API 契約の仕様書に、機械可読な契約は OpenAPI 形式の契約ファイルに定義する。本書にコードの情報は含まれない。

---

## 1. 設計原則

### 1.1 非エンジニアでも迷わない公開体験

novnow 形式の作品を持つ人は、Git・コマンド・ホスティングの知識がなくても、数回のクリックと URL の貼り付けだけで作品を Web 公開できること。公開フローの途中に「リポジトリ」「コミット」などの専門用語を必須の判断として出現させない。裏側の仕組みは隠蔽され、必要になったときだけ詳細を開けること。

### 1.2 契約先行とバックエンド非依存

フロントエンドが依存するのは novnow-hub 自身の API 契約だけである。契約の裏側（保管先・実行環境・外部サービス）は差し替え可能であり、差し替えによって API 契約とフロントエンドの振る舞いは変わらないこと。この契約はバージョン付き REST/JSON とし、OpenAPI 形式で機械的に検証可能な形で別途提供する。

### 1.3 最小サーバーコストと OSS

本プラットフォームは OSS として公開し、個人・小規模コミュニティでも無料〜極小コストで運用できることを設計の硬い制約とする。常時起動の専用サーバーを前提とせず、既存の無料枠の大きいサーバーレス環境や、低価格な VPS でも成立する構成を許す。

### 1.4 GitHub を土台としつつ、いつでも完全に剥がせる

初期フェーズでは GitHub を土台とする。公開プロジェクトの実体は GitHub リポジトリであり、変更提案・課題管理も当初は GitHub のものを利用する。ただしこの依存は一時的な実装選択であって、製品の恒久的な前提ではない。GitHub へのアクセスはポートと呼ばれる境界の背後に隠蔽され、その先でのみ GitHub の概念が現れる。後日 GitHub を別基盤に差し替えても、API 契約・フロントエンド・利用者の体験は変わらないこと。

### 1.5 データ主権と可搬性

作品データは常に利用者（またはその所属）の GitHub アカウント上に通常の git リポジトリとして存在する。サービスが消滅・終了しても、作品は通常のリポジトリとして残る。利用者はいつでも zip 取得・git clone・他ホストへの移行ができること。

## 2. 用語

| 用語 | 定義 |
|---|---|
| novnow 形式 | 小説・ノベルゲーム・シナリオなどの世界観を管理するプレーンテキスト中心のファイル形式。`project.toml` を中心に、本文・プロット・登場人物・用語辞書・資料などを UTF-8 テキストで管理する |
| novnow プロジェクト | novnow 形式のファイル一式を格納した自己完結フォルダ。Git でそのまま差分管理できる |
| novnow-hub（本プラットフォーム） | novnow 形式の作品を公開・共有・派生させるための Web プラットフォーム。本書の「hub」と同義 |
| hub プロジェクト | hub 上で公開された作品の単位。初期フェーズでは 1 つの GitHub リポジトリに対応する |
| 原作者 | 作品を最初に公開した利用者。hub プロジェクトの所有者となる |
| 二次創作者（派生作者） | 公開された作品を土台に、派生作品（二次創作・翻案・続編など）を作る利用者 |
| 公開 | hub プロジェクトを作成し、外部から閲覧・セットアップできる状態にすること |
| 派生（フォーク） | 既存の hub プロジェクトから自分のコピーを作成し、自分の作品として編集・公開できるようにすること |
| 変更提案 | hub 上での変更の提案単位。レビューの上で親プロジェクトへ取り込む。初期フェーズでは GitHub の Pull Request に対応する |
| 課題（Issue） | hub 上での課題・要望・議論の単位。初期フェーズでは GitHub の Issue に対応する |
| 自動マージ | 定められた条件（承認・検証通過など）を満たした変更提案を、機械的に親へ取り込む仕組み |
| チャット | hub プロジェクトに付随するリアルタイム寄りの会話の場 |
| セットアップ | novnow アプリ（デスクトップ版・ブラウザ版）が作品を開ける状態に自動で準備すること（必要なファイルの取得・初期化） |
| セットアップ URL | novnow アプリに「この hub プロジェクトをセットアップして開く」と伝える URL。URL ひとつでセットアップ済みの作品をアプリで開ける |
| pre-setup ビュー | アプリのインストールやセットアップなしに、ブラウザ上で作品（本文など）をそのまま読めるビュー |
| ポート | 外部基盤へのアクセスを抽象化する境界。hub API 側の語彙だけを使い、GitHub などの具体名を含まない |
| アダプター | ポートの実体を持つ実装。初期フェーズでは GitHub に対する実装を提供する |
| Phase 1 / Phase 2 | Phase 1 は GitHub を土台とした提供形態。Phase 2 は hub 自身のバックエンドへ置き換えた提供形態。利用者から見える契約は共通 |

## 3. 全体像

### 3.1 利用者と役割

- 原作者: novnow プロジェクトを hub に公開し、派生作品の動向を見守り、変更提案をレビューする。
- 二次創作者: 興味を持った作品の URL を novnow アプリに渡すだけで環境を整え、派生作品を作って再公開する。
- 読者: ブラウザで本文や設定資料をそのまま読む。アカウントなしでも公開作品を読める。
- 共同制作者: 招待され、同一作品に対して変更提案・課題・チャットで協力する。
- 運営者: OSS のセルフホストまたは少数の共有インスタンスを運用する。

### 3.2 システムの輪郭

システムは 3 つの輪で構成される。

1. クライアント群: ブラウザ版 Web アプリ（PWA）、および Tauri によるデスクトップ／モバイル相当のネイティブ版。同一のコードベースを共有し、見た目と操作は共通とする。
2. hub API: クライアントが唯一依存する、バージョン付き REST/JSON の API。認証・公開・閲覧・変更提案・課題・チャット・通知・novnow 特化機能を提供する。
3. 外部基盤: Phase 1 では GitHub（保管・変更提案・課題）と、hub 管理の軽量ストア（チャット・通知など揮発性の低い付随データ）で構成する。外部基盤は hub API の背後に隠蔽される。

クライアントは GitHub と直接通信しない。GitHub のアクセストークンをクライアントに保持させず、hub API が代理してアクセスする。

### 3.3 フェーズ構成

- Phase 1（GitHub 土台）: 公開プロジェクトの実体は GitHub リポジトリ。変更提案・課題は GitHub のものを API が代理操作する。hub は認証（GitHub OAuth）・プロジェクトの発見・novnow 特化機能・チャット・通知を担う。サーバーレス環境にフロントエンドと API をデプロイし、運用コストを最小化する。
- Phase 2（自前バックエンド）: GitHub アダプターを hub 自前のストレージ（組込 DB 等）のアダプターへ置き換える。API 契約とフロントエンドは変えない。
- 各フェーズの切り替えは、ポートの実装差し替えだけで完結しなければならない。

## 4. アカウントと認証

### 4.1 サインイン（GitHub OAuth）

- サインインは GitHub OAuth のみを提供する。novnow-hub 独自のパスワード認証は提供しない。
- サインインに必要な権限は最小限とする（プロフィールの読み取りと、公開用リポジトリの作成・操作に必要な範囲）。
- サインイン時に GitHub の利用規約・プライバシーと、hub の利用規約・プライバシーポリシーへの同意を表示する。
- 初回サインイン時に hub 上の利用者像が作成される（表示名・アイコンは GitHub の公開情報を既定値とし、後から変更できる）。

### 4.2 権限モデル

- hub API へのアクセスは、プロジェクト単位の役割（所有者／共同制作者／読み取り専用）と、認証の有無（公開読み取りは匿名可）の組合せで認可する。
- 役割は Phase 1 では GitHub の権限から導出し、hub 独自の権限管理は持たない。Phase 2 では hub 自身が権限を保持する。権限判定の語彙と粒度は両フェーズで共通とする。
- 破壊的操作（プロジェクトの非公開化・削除、派生元の表示、権限変更）は所有者のみ実行できる。

### 4.3 サインアウト・退会

- サインアウトするとセッションは即時失効する。
- 退会すると hub 上の利用者像・通知・セッションは削除され、GitHub へのアクセス許可（OAuth トークン）は失効する。作品（GitHub リポジトリ）は利用者自身の資産として GitHub 上に残り、hub 側からは一覧されない。

## 5. プロジェクトの公開

### 5.1 新規公開フロー

- 画面の指示に従い、(1) GitHub でサインイン、(2) 手元の novnow プロジェクトを選択または zip をアップロード、(3) タイトル・説明・ライセンス・公開範囲を確認、の 3 ステップで公開できる。
- 公開処理は、GitHub 上にリポジトリを作成し、初期ファイル群を 1 回のコミットで投入し、hub プロジェクトとして登録する一連の操作を原子的に近い形で行う。途中で失敗した場合は中間状態を残さず、やり直せること。
- 公開完了後、公開ページの URL とセットアップ URL を提示する。

### 5.2 公開プロジェクトの実体

- Phase 1 では 1 つの hub プロジェクトが 1 つの GitHub リポジトリに対応する。リポジトリ名の既定は作品名から機械的に生成し、重複時は一意の接尾辞を付す。
- 公開ページの正規 URL は hub のドメイン上に置かれ、GitHub の URL とは独立した形で提示する（GitHub へは遷移リンクとして併記してよい）。
- 作品のソースと履歴の正は GitHub 側にあり、hub は表示用の情報を自前に保持しすぎない。

### 5.3 novnow 形式の検証

- 公開前に novnow 形式としての妥当性を検査する。必須要素の欠落、文字コードの不正、`project.toml` の版が本体より新しい等の場合は公開を拒否し、何を直せばよいかを利用者の言葉で示す。
- 構文エラーなど「開けなくはないが怪しい」内容は、公開は許可するが警告として列挙する（原文は一切書き換えない）。
- 検証は GitHub への投入前に行い、壊れた初期状態を作らない。

### 5.4 可視性とライセンス

- 可視性は公開（全世界）・非公開（所有者と共同制作者のみ）の 2 区分を Phase 1 で提供する。Phase 1 の非公開は GitHub リポジトリの可視性に従う。
- 公開時にライセンスの選択を必須とする。選択肢は CC0／CC BY／CC BY-SA／CC BY-NC／カスタム（全文記述）とする。ライセンスは公開ページとメタ情報に表示する。
- 派生可能なライセンスかどうかを機械的に判定し、派生ボタンの活性・非活性に反映する（CC BY-NC 等の派生制限がある場合は警告を出す）。

### 5.5 更新と版

- 作品の更新は、原作者が手元で編集し hub 経由または GitHub 経由で取り込む。hub は取り込みのたびに公開ページ（本文ビュー）を再生成する。
- git の履歴がそのまま作品の履歴である。hub は独自のリビジョン番号を作品の正として持ち込まない。
- Releases 相当の「版を切る」操作を hub 上から行える（リリースノート・版番号タグの作成）。

## 6. 閲覧と発見

### 6.1 プロジェクトページ

- 公開ページには、タイトル・説明・作者・ライセンス・最新更新日時・派生数・主要なファイル構成を表示する。
- 本文ビューでは、novnow 形式の本文を読者向けの体裁（注釈記号を除去した表示）に整形して表示する。編集導線は所有者・共同制作者にだけ表示する。
- 設定資料（登場人物・用語辞書・プロット概要など）は、作者が「公開資料」として選んだものだけをタブ等で表示する。資料は既定で非公開とする。
- ページ下部に関連作品・派生作品への導線とライセンス表示を置く。

### 6.2 一覧と検索

- 公開作品の一覧は、新着・更新順・人気順で並び替えられる。ページネーションは無限スクロールではなく明示的な「次へ」で行う（アクセシビリティと低速回線を考慮）。
- 検索は、キーワード・タグ・ライセンス・novnow の種別で絞り込める。Phase 1 では GitHub の検索に依存しすぎず、hub 側の軽量インデックスで実現する。
- ランキングやトレンドなど重い集計は提供しない（コスト制約）。

### 6.3 ブラウザでそのまま読む

- アカウントなし・アプリなしで、公開ページの URL を開くだけで本文を通読できること。
- 読書体験はダーク／ライトテーマと文字サイズ調整をサポートする。読書位置の保存は任意（端末内）とする。
- novnow 特有の非表示指定（注釈・コメント）は読者ビューに現れない。

## 7. 二次創作支援（novnow 特化）

### 7.1 URL ワンクリックセットアップ

- 公開ページの「novnow で開く」から発行されるセットアップ URL を novnow アプリ（デスクトップ／ブラウザ）が解釈し、次を自動で行う: 作品の取得 → ローカルへの配置 → novnow プロジェクトとしての初期化検証 → エディタを開く。
- URL には hub プロジェクトの識別情報のみを含み、認証情報や個人情報を含まない。
- セットアップ URL はブラウザ版へは通常の URL として渡し、デスクトップ版へは OS のカスタムスキームで渡す。いずれも同じ URL の意味を持つ。
- セットアップに失敗した場合は、どの工程で失敗したかと手動での取得方法（GitHub 上のプロジェクトページ）を示す。

### 7.2 派生作品の作成（フォーク）

- 公開ページの「派生作品を作る」から、数クリックで自分の hub プロジェクトを作成できる。処理は GitHub のフォークに相当するコピーを作成し、派生元との対応関係を hub が記録する。
- 派生時には、ライセンス継承の確認・作品名の既定値・説明の初期値を提示する。
- 派生作品の初回公開時も novnow 形式の検証（§5.3）を通す。
- 派生の派生（孫作品）も同様に作成でき、派生元の連鎖を保持する。

### 7.3 派生作品から親作品への還元（変更提案）

- 派生作品で行った改善（誤字修正・設定の矛盾指摘・用語の追加など）を、親作品へ変更提案として送れる。操作は「親へ提案する」から差分を確認して送るだけとする。
- 親作品の所有者は、提案の差分・提案者・発言を確認し、承認・コメント・却下ができる。承認済み提案は自動マージの対象にできる（§8.2）。
- 提案は本文テキストの差分として表示され、novnow 形式の診断結果（新たに混入した誤り）も併せて表示する。

### 7.4 派生ツリーの可視化

- 各プロジェクトページに「派生」タブを設け、自分の直接の子作品・孫以降・兄弟作品を木構造で表示する。各ノードはタイトル・作者・更新日・派生可否を示す。
- 原作者は派生作品の存在を通知で知る（§9）。通知は設定で切れる。

### 7.5 novnow 診断・エクスポート連携

- hub 上で novnow の診断（novnow check 相当）を実行し、結果を「点検」タブに表示できる。診断の実行は変更提案の必須チェックにも利用できる（§8.5）。
- hub 上で本文のエクスポート（注釈除去済みテキスト／Markdown）を生成できる。生成物はダウンロードまたは提案に添付できる。
- これらの重い処理は非同期ジョブとして実行し、完了を通知で知らせる。hub 自身は novnow 本体の全機能を再実装しない。

## 8. コラボレーション（GitHub 型）

### 8.1 変更提案（プルリクエスト）とレビュー

- 変更提案は、タイトル・説明・差分・会話・状態（オープン／承認済み／取り込み済み／却下）を持つ。
- 差分は本文テキストと設定ファイルの単位で表示し、novnow 形式の診断差分（新規混入／解消）を添える。
- レビューはインラインコメントと全体コメントの両方をサポートする。
- Phase 1 では提案の実体と会話は GitHub の Pull Request に保存し、hub は表示と操作のファサードを提供する。

### 8.2 自動マージ

- 変更提案ごとに「条件を満たしたら自動で取り込む」を予約できる。条件は次を組み合わせ指定する: 必要な承認数（既定 1）／必須チェックの通過／競合がないこと。
- 自動マージの実行主体は Phase 1 では GitHub の自動マージ機構、または hub の定期実行を用いる。結果（取り込まれた／条件未達／競合で失敗）は提案の会話と通知に反映する。
- 自動マージが発火したことは誰が操作したかを含めて記録に残す。

### 8.3 課題（Issue）

- 課題はタイトル・本文・ラベル・状態（オープン／クローズ）・担当者・会話を持つ。
- 課題テンプレートを作品ごとに用意できる（例: 誤字報告／設定の矛盾／展開の提案）。
- 課題から変更提案への紐付け（この提案は課題 X を解決する）を記録できる。

### 8.4 チャット

- プロジェクトごとに 1 つ以上のチャットルームを持つ。ルームは全体／制作／雑談など任意の名前で作成できる。
- メッセージは時系列表示・未読バッジ・編集・削除（論理削除）をサポートする。
- メンション（@表示名）で通知を送る。
- チャットは揮発性の低い付随データであり、hub 管理の軽量ストアに保存する。GitHub には保存しない。

### 8.5 CI（マージ前検証）

- 変更提案の必須チェックとして「novnow 点検」（診断エラー 0 件）を登録できる。チェックの実行は hub 管理のジョブまたは外部の CI（GitHub Actions 等）の結果を取り込んでよい。
- チェック結果は変更提案に表示され、自動マージの条件に使える。
- 重いチェックは非同期に行い、提案をブロックしすぎない（結果待ちのまま数日放置されないよう、未完了は明示する）。

## 9. 通知

### 9.1 通知センター

- hub 内の通知は通知センターに集約する。対象は、派生作品の作成・変更提案・その承認/取り込み/自動マージ結果・課題の作成/コメント・チャットのメンション・点検ジョブの完了・公開の再生成完了。
- 通知は未読/既読/全既読ができ、種別でフィルタできる。一覧はページネーションを持つ。

### 9.2 通知チャネル

- 既定は hub 内のみ。任意でメール通知・Web Push を有効化できる。チャネルごと・種別ごとに有効/無効を設定できる。
- メール通知はオプトインとする（コストと同意の観点）。
- Phase 1 でメールを提供しない場合、通知チャネルの設定 UI は hub 内通知のみを表示し、将来の拡張として無効化しておく。

## 10. 非機能要件

### 10.1 性能目標

- 公開ページの初回表示は、国内モバイル回線で 2 秒以内の Largest Contentful Paint を目標とする。本文データは静的配信または CDN キャッシュを優先する。
- hub API の読み取り系エンドポイントのサーバ処理時間は p95 で 200 ミリ秒以内を目標とする（外部 API 往復を除く構成では 100 ミリ秒以内）。
- 検索は 300 ミリ秒以内を目標とする。

### 10.2 可用性

- Phase 1 は可用性を GitHub と選定したサーバーレス基盤に依存する。hub 自身の月間可用性目標は 99.5% とする。
- GitHub 障害時は、公開ページの静的部分は配信を継続し、書き込み系操作のみ一時的に利用不能とする（読み取り専用に縮退する）。
- 縮退中はその旨を利用者に明示する。

### 10.3 セキュリティとプライバシー

- 認証トークン・OAuth シークレットはクライアントに永続させず、hub API 側で安全に管理する。
- 公開作品以外のファイル内容（非公開作品・未公開の変更提案のソース等）を、認可を経ずに返さない。
- 利用者のメールアドレス等の GitHub から得た個人情報は、表示名・アイコンに必要な最小限だけを保存する。
- アップロードされた zip は検証後に破棄し、恒久保存しない。
- CSRF・クリックジャッキング・XSS・パストラバーサル（zip 内の `../` 等）への対策を行う。

### 10.4 コスト制約

- 共有インスタンスの運用コストは、GitHub とサーバーレス無料枠＋最小限の有償枠のみで、月額数千円以下を目安とする。
- 定時実行（cron）の頻度・実行時間に上限を設け、従量課金の暴走を防ぐ。
- 重い処理（エクスポート・診断）はキュー化し、同時実行数を制限する。

### 10.5 アクセシビリティと国際化

- Web アプリはキーボード操作とスクリーンリーダーに対応する（WCAG 2.1 AA 相当を目標）。
- UI は日本語・英語を初期言語とする。表示文字列は辞書化し、将来の言語追加を阻害しない構造にする。
- 日時は協定世界時で保持し、表示は利用者のロケールとする。

### 10.6 ライセンスとガバナンス

- hub のソフトウェアは OSS ライセンス（本リポジトリの LICENSE に従う）で公開する。
- 仕様・契約・運用方針はリポジトリ内のドキュメントで公開管理し、変更は人間の承認を経る。
- 公開インスタンスの運営ポリシー（公開基準・削除基準・著作権対応）を明記する。

## 11. 将来の拡張点

### 11.1 Phase 2（hub 自前バックエンド）への移行

GitHub 依存を完全に除去し、同一の API 契約のまま hub 自前のストレージによる提供へ切り替える。

### 11.2 セルフホスト配布物の拡充

ワンクリックデプロイ、導入ガイド、GitHub からの移行ツールなど、自前運用の敷居を下げる配布物を提供する。

### 11.3 作品内検索の高度化

全文検索と、重い集計を伴わない範囲での類似作品レコメンドを提供する。

### 11.4 novnow 本体との双方向連携の強化

設定の同期、診断設定の共有、アプリからの直接公開など、hub と novnow アプリの連携を深める。

### 11.5 プラグイン的な拡張

独自ライセンステンプレート・独自検証ルールなどを、安全性を保ちながら追加できる拡張機構を提供する。

### 11.6 通知チャネルの追加

Web Push・メール・外部チャット連携など、通知の届け先を増やす。

### 11.7 出所証明

コミット署名や透明性ログにより、公開作品の出所と改変履歴を検証可能にする。
